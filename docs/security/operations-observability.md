# Operational measurements and response

Enable server-only TASTEPOLICY_OPERATION_METRICS=true on the exact verified release to emit JSON log records named tastepolicy_operation_v1. The default is disabled until deliberately configured. Records contain only the timestamp, fixed surface/outcome enums and bounded integer duration. They omit identities, tenants, candidate IDs, queries, preference contents, bodies, credentials, error text and URLs. Logging failure cannot alter authorization. Tests exercise runtime allowlists and payload non-disclosure.

REST, MCP, A2A and OAuth wrappers record HTTP failure rates and wall latency. MCP tool execution errors have a separate MCP_TOOL/ERROR counter because a tool error may use HTTP 200. Do not combine that counter with HTTP request denominators. Qloo adapter measurements cover provider result availability after shape validation; they contain no cultural evidence. Database readiness probes measure migration-ledger reachability/latency. State snapshot decision measurements record ALLOW, ASK, REJECT or UNAVAILABLE and component elapsed time before persistence. Retries or unsuccessful persistence can generate multiple component events; the authenticated workspace's stored decision counts are the source for durable usage and billing, not log counts.

Compute rates per fixed surface and time window, and p50/p95 of recorded latency. For the state snapshot cohort, ASK/(ALLOW+ASK+REJECT+UNAVAILABLE) and REJECT/the same denominator can identify changes requiring investigation. They are operational signals, not correctness labels or customer-preference analytics. Other evaluator paths are not covered by this component cohort. Never infer all-platform decision volume from it.

The Production monitor workflow runs read-only checks from GitHub infrastructure every 15 minutes after the workflow is merged to main. It records liveness, database/migration readiness, OpenAPI, agent-card origin and OAuth issuer. Artifacts expire after fourteen days. GitHub schedule execution is best effort and may be delayed; a configured workflow is not evidence of a completed run or delivered alert. Existing account workflow notifications are not verified paging. Check the Actions page for failures; no 24/7 on-call/SLA is promised. A managed alerting destination and its delivery drill remain uncommissioned.

The monitor does not exercise clean signup, OAuth rotation, authenticated MCP tools or Qloo network reachability. Those remain separate hosted release acceptance. Vercel logs are provider-plan-dependent; no durable metrics collector, log drain, long-term dashboard or retention guarantee is claimed. Do not enable customer telemetry vendors without vendor-register/privacy review. Retention automation and redaction must be rechecked when a destination is commissioned.

Triage: compare a failing monitor to /api/ready and exact deployment revision, inspect only sanitized operation records and request IDs, then follow operations.md and the migration rollback runbook. A Qloo outage yields explicit UNAVAILABLE where required; never fail open to ALLOW or turn a price/authority restriction into a retry authorization. A database problem must not produce a guessed policy decision. No unsupported load/capacity claim follows from these probes.
