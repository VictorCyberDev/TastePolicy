# "TastePolicy Compatible" — attestation profile

This page defines what a project may mean when it says its software is **TastePolicy Compatible** for attestations. TastePolicy does not certify or endorse third parties. A statement is a claim by that project, valid only for the stated software version and vector-set version.

## Scope

Compatible means: a **verifier** that accepts and rejects TastePolicy attestations exactly as the vectors require. It does not mean a project issues attestations, speaks for TastePolicy, or may imply TastePolicy approves its product or any action taken on an attestation. An attestation grants cultural authority only (`authority: CULTURAL_ONLY`); a Compatible verifier must never treat one as purchase, payment, booking or private-data authority.

## Profile

- Container: SD-JWT, RFC 9901. Algorithms `ES256` or `Ed25519`; `none`, symmetric and unlisted algorithms rejected.
- Header `typ: dc+sd-jwt`. Claims follow SD-JWT VC `draft-ietf-oauth-sd-jwt-vc-19` (a draft; this profile is _aligned with_ it, not certified against it).
- Required visible claims: `iss`, `aud`, `iat`, `exp`, `jti`, `vct` (`https://tastepolicy.dev/vct/preference-authority/v1`), `authority: CULTURAL_ONLY`, `status.status_list.{idx,uri}`. Optional `cnf.jwk`.
- Status: Token Status List `draft-ietf-oauth-status-list-21`, `statuslist+jwt`, 2-bit statuses (0 VALID, 1 INVALID, 2 SUSPENDED).
- A verifier is configured with a trust list (issuer, keys, accepted `vct`) and an expected audience. It must not discover trust from the presented token.

## Required behaviour (vector set `tastepolicy-attestation-vectors-v1`)

A Compatible verifier accepts V01–V04 and rejects N01–N36 for the reasons listed. In short, it must reject: expired or not-yet-valid tokens; wrong audience; issuers or keys it was not configured with; altered payloads or disclosures; duplicate or unreferenced disclosures; unsupported algorithms (including `none` and `HS256`) and untrusted key-bearing headers (`jwk`); wrong `typ`; unaccepted `vct`; a missing authority statement or authority epoch (`EPOCH_MISSING`, N36); missing, invalid, suspended, out-of-range, forged, expired or mis-addressed status lists; oversized (decompression-bomb) status lists; missing or wrong key binding (nonce, audience, `sd_hash`, holder key); and replay of a `jti` for an audience. Failing closed on any status fetch error is required.

## Running it

```sh
npm run conformance:attest -- path/to/your-adapter.mjs [--strict-reasons]
```

Your adapter default-exports `async ({presentation, audience, now, nonce, trustedIssuers, statusLists, seenJtis}) => ({valid, reason?})`. `statusLists` maps status URIs to the status list tokens to use (no network access should be needed). Without an argument the runner uses TastePolicy's reference verifier (`scripts/conformance/reference-adapter.ts`). `--strict-reasons` additionally requires the first reason code to match; reason names are TastePolicy's and are optional for third parties.

The vector file is regenerated by `npm run conformance:attest:generate` (fresh test-only keys; ES256 signatures are randomized, so regeneration changes the file). Vector sets are versioned; a claim must name the version.

## What it does not cover

Issuance, hosted status serving, key rotation, OAuth/OpenID4VC wallet protocols, the SD-JWT VC Type Metadata and display sections, and any claim about the person's data.

## Profile `tastepolicy-compatible-v1`

The suite is versioned independently of the draft specifications it uses. Groups, all run by `npm run conformance:compatible`:

| Group               | Data                                           | Covers                                                                                                                                                              |
| ------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| attestation         | `conformance/attestation-vectors-v1.json` (40) | signature, algorithms, audience, expiry, status (incl. permanence), epoch, replay, selective disclosure, key binding, issuer trust states (T01–T04), key revocation |
| authority semantics | `conformance/authority-semantics-v1.json`      | typed ASK (authority confirmation vs clarification), continuation sets, lease/epoch transitions                                                                     |
| issuer metadata     | `conformance/issuer-metadata-vectors-v1.json`  | boundary, algorithms, origin binding, key lifecycle, "discovery grants no trust"                                                                                    |

Decision semantics of M6 (ALLOW/ASK/REJECT/UNAVAILABLE, UNAVAILABLE is never REJECT, hard rules final) are covered by the repository tests, not by portable vectors yet; an implementation can claim only the groups above.
