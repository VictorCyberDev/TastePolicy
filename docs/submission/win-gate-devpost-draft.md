# Devpost draft — NOT SUBMITTED

Project: TastePolicy

Tagline: Preference authorization for autonomous agents.

Problem: memory and tool permission do not establish whether a subjective choice is justified for a particular person or group in context.

Solution: explicit cultural signals and user-controlled state/context/constraints + Qloo-grounded cultural evidence → deterministic ALLOW / ASK / REJECT / UNAVAILABLE → auditable receipt + bounded agent continuation. No transaction authority.

Why Qloo: it supplies entity identity, cross-domain cultural relationships, candidate-specific evidence and explainability where supported. TastePolicy supplies preference authority, subject separation, explicit rules and uncertainty. It does not own Qloo's graph.

Difference from a recommender: discovery asks what a person might like; authorization asks whether this specific agent proposal is justified under the person's configured state/context and applicable rules. A cultural score cannot override a hard exclusion.

Technology: Next.js/TypeScript modular monolith, server-only Qloo, PostgreSQL immutable state, deterministic evaluator, scoped feedback, bounded clarification/repair, TasteTrajectory, separate proxies and unanimous/no-veto groups, captured receipts and M1.6 local agent interface. No staged M6 authentication/Passport/SDK or A2A is included in this branch.

Proof: see current Win Gate report for exact CI/test/provider/human status. No human accuracy, live hosted persistence or free LLM baseline is claimed without evidence. Known accepted historical Qloo evidence is labeled RECORDED LIVE ACCEPTANCE. Current human pilot N=0.

Impact hypothesis: concierge/travel and preference-sensitive commerce teams need auditable stop/ask behavior before separate execution approval. No market-size or revenue claim.
