# ADR 0013 — Agent2Agent (A2A)

Status: accepted for M6G. Recorded before implementation. Evidence: primary-source research of 2026-10-23.

## Protocol and version

| Item          | Value                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Protocol      | Agent2Agent (A2A), JSON-RPC over HTTP binding                                                                             |
| Specification | **1.0.x** — 1.0.0 released 2026-03-12, 1.0.1 (patch) 2026-05-26 — https://a2a-protocol.org/latest/specification/          |
| Normative     | `specification/a2a.proto` in https://github.com/a2aproject/A2A; JSON Schema https://a2a-protocol.org/latest/spec/a2a.json |
| Governance    | Linux Foundation, Agentic AI Foundation (Growth Stage project, announced 2026-08-27)                                      |
| Earlier       | 0.3.0 (2025-07-30), still consumed by some vendors                                                                        |

Only `Major.Minor` ("1.0") is used on the wire. The spec prose contains inconsistent 0.3 examples inside 1.0 text; the proto and "What's new in v1" are treated as authoritative.

## Decision

- Hand-roll a minimal, conformant **1.0 JSON-RPC** handler in a Next.js route handler instead of adopting `@a2a-js/sdk` 1.3.0 (Apache-2.0). Reasons: the SDK is Express-centric, brings task/event-bus/store machinery we do not need, ships a per-instance in-memory task store unsafe on serverless, and moves fast (six releases in three months); our authentication and receipt storage already exist; the surface is one skill. The SDK and the official TCK are used for **testing**, not as a runtime dependency.
- Discovery: `GET /.well-known/agent-card.json` (public, cacheable, no secrets). One interface (`protocolBinding: JSONRPC`, `protocolVersion: "1.0"`) at `/api/a2a`. `capabilities`: streaming false, pushNotifications false, extendedAgentCard false.
- One skill, `preference_authorization`: "Evaluates whether a preference-sensitive subjective choice is sufficiently justified for an authorized subject." It does not authorize purchase, booking, payment or any execution.
- Methods: `SendMessage`, `GetTask`; `CancelTask` returns `TaskNotCancelable`/`TaskNotFound`; every other method returns the spec's not-supported error. `A2A-Version` is enforced (`VersionNotSupportedError` -32009; a missing header is treated as 0.3, which we reject with the same error).
- `SendMessage` is blocking and returns a **Task** in `TASK_STATE_COMPLETED` carrying one artifact whose parts are a `data` part (the same authorization response the REST API returns) and a `text` summary (some consumers are text-only). The evaluation operation completing is COMPLETED, including a decision of UNAVAILABLE, exactly as in REST (`status: COMPLETED` does not mean evidence was available). Genuine failures (access denied, invalid input, state conflict, infrastructure) are JSON-RPC errors, never ALLOW. `TASK_STATE_REJECTED` is not used for a REJECT decision (semantic overload risk). `messageId` is the idempotency key. The task id is the evaluation reference, so `GetTask` is stateless and reads the stored receipt.
- Authentication at the HTTP layer on every request: `Authorization: Bearer` developer credential, scope `TASTE_EVALUATE` (and `RECEIPT_READ` for `GetTask`). Identity is derived only from the verified credential, never from `tenant`, message content or claimed subject. `GetTask` returns `TaskNotFound` for tasks outside the caller's boundary (spec §13.1; no existence leak).

## Features used / not used

Used: Agent Card, `supportedInterfaces`, `skills`, `securitySchemes` (HTTP bearer, plus OAuth when ADR 0014 lands), `SendMessage`, `GetTask`, Task/Artifact/Part, spec error codes with `google.rpc.ErrorInfo`.

Not used: streaming, push notifications, extended Agent Card, signed cards (a possible M9 hardening), gRPC and HTTP+JSON bindings, `ListTasks`, `AUTH_REQUIRED`/`INPUT_REQUIRED` task states (stateless), multi-turn tasks.

## Security implications

Server must authenticate every request (spec §7.4), scope tasks to the caller (§13.1), and keep the public card free of secrets. `AUTH_REQUIRED` is not an authorization mechanism. Rate limits and provider budgets apply as for REST/MCP.

## Compatibility requirements and known gaps

- Gemini Enterprise registration documents only A2A **0.3** and end-user OAuth bearer tokens; it ignores card `securitySchemes` and cannot send static API keys. A 1.0 card therefore does not satisfy it. A 0.3-compatible shim is optional follow-on work and is **not claimed**.
- Microsoft Foundry's A2A tool supports GA 1.0 (JSON-RPC, text only, no streaming); Copilot Studio supports an API-key header. These are untested by us.
- Conformance is checked with the official `a2a-tck` and `a2a-cli` where they can run unauthenticated or with a test credential; unsupported operations are expected to be reported, not hidden.
