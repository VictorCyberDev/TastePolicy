# TasteBench v2: synthetic boundary coverage

This expands engineering coverage from the original 24 scenarios without replacing that dataset or rewriting the human pilot. It does not establish real taste relevance or a defensibility moat.

525 synthetic combinations cover three candidate domains, seven affinity/provider states, five rule scopes and five price contexts. Inputs and results are committed in benchmarks/tastebench/v2. Neutral hashed IDs avoid embedding expected answers in candidate names. A deterministic SHA-256 partition allocates 393 calibration and 132 evaluation cases. This is a coverage partition, not independently collected held-out validation. Existing provisional 0.5/0.8 thresholds are unchanged; neither partition was used to tune them.

The explicit contract oracle prioritizes independent hard blocks, provider unavailability, weak cultural evidence, unresolved applicable price constraints, then strong/uncertain alignment. The STATE_POLICY adapter invokes the actual stateDecision component with a real receipt generated from synthetic cultural evidence. Its Qloo-shaped provenance is a fixture required by the receipt schema; there are no live Qloo calls in this experiment. AFFINITY_ONLY uses the same cultural threshold policy without user authorization rules; it is not a claim about Qloo's own authorization product. CONSERVATIVE_RULES rejects hard blocks and otherwise asks; it is deliberately simple and does not consume provider availability. A separate prompt-only ChatGPT observation is documented below; it is not pooled with these 132-case adapter metrics.

These scores demonstrate this contract's boundaries and the cost of omitting them, not superiority on real-world recommendation quality. Rules and oracle share the same written specification, so perfect component accuracy is expected regression behavior. Recommendations/taste relevance are not measured. Drift, lease, epoch, commitments and proof safety are tested separately by lifecycle and conformance suites and are not assigned synthetic scores here. Timing from an engineering run is not production capacity evidence.

Reproduce with `npm run tastebench:boundaries`. Intentional version changes use the same command plus `--write`; review dataset/result diffs and record the source revision. The default command recomputes and checks the dataset hash and every stored prediction/metric; it fails on drift. The generator's recorded sourceRevision identifies the checkout used, while the generator itself is versioned in the containing commit. Dataset hash: da214ea5758e3db15e3f95aa1168efa18483bdfeaa5617fd6e25d62dd5a3d801.

The historical operator-asserted human pilot remains counterevidence: 94/160 exact decisions, 14/150 unsafe autonomy, 33/67 missed ASK, 2/10 incorrect REJECT and 9/32 correct UNAVAILABLE. Its ten participants and 180 repeated judgments were not independently recruited/verified; twenty judgments were unscorable. Do not pool those figures with synthetic coverage or call them validated customer research.

## Prompt-only ChatGPT observation

On 2026-10-29, a fresh signed-in ChatGPT conversation received the complete written contract and sixteen cases selected before inference: the first sixteen evaluation IDs in lexical order. No TastePolicy tool, connector, Qloo request or private data was used. The browser exposed no exact model/version, temperature or seed. The actual response and prompt are preserved in benchmarks/tastebench/v2/chatgpt-prompt-observation.json with a prompt hash and per-case scoring; the clipped screenshot is assets/chatgpt-synthetic-baseline-20261029.jpg.

Against the synthetic contract: 13/16 exact, one unsafe ALLOW among fifteen non-ALLOW cases, one missed ASK among eight ASK cases, zero incorrect REJECT among ten non-REJECT cases and one of one required UNAVAILABLE recognized. This is one prompt and one batch on sixteen convenience cases, without independent replication. It supports a narrow observation about that response, not a model-wide failure rate, recommendation relevance, general safety claim or competitive victory. Giving the full contract makes this a prompt-policy baseline without a dedicated runtime enforcement layer. It is not evidence that the TastePolicy MCP integration worked in ChatGPT.

## Integrated gateway adapter

The same 132 evaluation cases also run through a separate offline integration adapter: actual Better Auth signup/session records, scoped credential issuance, SDK requests, REST request validation, owned state lookup, policy decision, receipt persistence, captured replay integrity and cross-owner refusal. Synthetic constraint snapshots and matching mutation records are seeded only in the isolated benchmark database; this is not proof of an owner feedback UI. The provider returns explicitly synthetic Qloo-shaped identities/evidence, with no outside network requests. The action is SUGGEST and there is no active policy override. MCP/A2A hosts, live Qloo relevance, lease/proof lifecycle and the browser are outside this adapter.

Local PGlite result: 132/132 exact, zero unsafe ALLOW among 126 non-ALLOW cases, zero missed ASK among 51 ASK cases, zero incorrect REJECT among 70 non-REJECT cases, 13/13 required UNAVAILABLE, and 31/31 hard rules honored with no provider call. All 132 receipts were captured and all 132 identical retries replayed without provider work; all 131 attempted reads of a different owner's Passport were denied. PGlite is not a concurrent PostgreSQL server. CI can execute the identical script against its isolated real PostgreSQL service through TASTEPOLICY_TEST_DATABASE_URL; that separate run must pass before claiming the PostgreSQL result.

Reproduce using npm run tastebench:gateway. Default mode compares all rows/metrics to integrated-results.json and fails on any contract, receipt, replay or cross-owner check failure. The --write option intentionally versions an observation; it still refuses a failed acceptance. No customer data, credential or raw auth identifier is written in the report. This widens the comparison framework beyond a pure policy function while retaining the original 24 scenarios and separating synthetic engineering results from legitimate human judgments.

## Separate lifecycle and proof measurements

The reference conformance run passes 153/153: attestation 40/40, ASK classification 9/9, continuation 4/4, lease semantics 10/10, issuer metadata 12/12, commitment vectors 21/21, canonical JSON 43/43 and action ladder 14/14. Lease sequence L05 specifically checks drift suspension followed by a new authority epoch on resume; the ten sequences also cover invalid approval, terminal non-revival and required prior suspension. These are published contract vectors, not empirical probabilities of detecting arbitrary future drift. Twenty-five additional focused lease-machine/commitment/attestation tests passed in the dated local run; full exact-head CI covers them separately.

Recommendation/taste relevance remains **NOT_ESTABLISHED**: the current fixtures assign synthetic cultural scores, and the legitimate existing descriptive pilot labels authority decisions rather than independent taste relevance. It would violate the product boundary to reinterpret authorization labels or Qloo affinity as human preference ground truth. A relevance experiment requires consented independent owner/context ratings of a frozen candidate set, with the same set and held-out partition supplied to all ranking systems. Report relevance separately (for example, a predeclared per-query ranking metric and its participant/context aggregation); do not infer it from the perfect contract scores above. No new participants or judgments have been invented.
